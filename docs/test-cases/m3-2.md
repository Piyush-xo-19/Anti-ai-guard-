# M3.2 runtime contract cases

[Runtime plan](../m3-plan.md#implementation-chunks) |
[Reducer](../../src/runtime.rs) |
[Synthetic fixtures](../../tests/runtime.rs)

Run from the repository root with the pinned Rust toolchain.

```powershell
cargo test --locked --offline --test runtime
```

Each fixture supplies synthetic process instances, receipt IDs, and elapsed
times. The reducer uses one run and source generation, keeps a fixed maximum
number of receipt IDs, and accepts a deadline measured from run start. It
retains no process observations. The source wall time is optional metadata
and has no effect on deadlines or health.

| Case | Fixture | Expected outcome |
| --- | --- | --- |
| M3.2-READY | Baseline before readiness, delayed earlier baseline, baseline after readiness | Only the last baseline can complete startup. |
| M3.2-UNKNOWN | Ready source with unknown loss reporting, baseline, then repeated readiness | Continuity stays degraded and the reducer preserves the original readiness declaration. |
| M3.2-RECEIPTS | Stop delivered before start, then a duplicate stop | First deliveries are accepted regardless of order. Repeat receipt is ignored. |
| M3.2-IDENTITY | Reused PID and missing creation time | Existing process-instance correlation reports different or indeterminate, respectively. |
| M3.2-STREAM | Events and loss from a different run or generation | No change to the active generation's deadline, health or receipt budget. |
| M3.2-BOUND | Fill the receipt ledger, offer a duplicate, then offer a unique receipt | The duplicate still deduplicates; the new receipt is refused and recorded as an interruption. |
| M3.2-LOSS | Report source loss or queue overflow after readiness and baseline | The first interruption remains visible through later markers and cancellation. |
| M3.2-UNAVAILABLE | Denied source followed by readiness and baseline | This generation stays unavailable. |
| M3.2-STOP | Deadline at exact boundary, silent run deadline, explicit cancellation | The reducer stops deterministically and late source inputs cannot reopen it. |

Healthy means that a caller-confirmed source, a subsequent reconciled baseline,
and an observable mechanism for reporting loss are present with no reported
interruption. It is a runtime diagnostic state. The fixtures exercise those
signals and transitions. Live receipt and source-reported loss visibility
remain M3.1/M3.3 work. A real bounded event queue, reconciliation, and generation
recovery are covered by later chunks in the runtime plan.
