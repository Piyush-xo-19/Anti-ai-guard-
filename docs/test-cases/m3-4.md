# M3.4 synthetic baseline reconciliation cases

[Runtime plan](../m3-plan.md) |
[Reconciler](../../src/runtime/reconcile.rs) |
[Tests](../../tests/reconciliation.rs)

Run using the pinned Rust toolchain from the repository root.

```powershell
cargo test --locked --offline --test reconciliation
```

The caller confirms source readiness, begins the snapshot, and supplies a
successful completed baseline. Process events arriving before completion use a
bounded FIFO buffer. The completed baseline and buffered events build a bounded
temporary evidence set, which replaces the published records only after success.

A stable matching process instance combines baseline, start and stop evidence.
Incomplete identity stays in separate records. Stop and start receipt order has
no effect on those evidence flags. Every record describes observed evidence,
with current liveness left unresolved. Source wall time stays outside deadline
calculations.

| Case | Expected result |
| --- | --- |
| M3.4-READY | Baseline capture requires readiness. Only finish_baseline can complete the baseline marker. |
| M3.4-INTERVAL | Events before, during and after the snapshot combine with baseline evidence only for matching instances. |
| M3.4-FAST-EXIT | A start and stop absent from the baseline remain recorded, including stop-first delivery and a duplicate receipt. |
| M3.4-IDENTITY | Reused PID, missing creation identity and missing boot identity remain distinct. |
| M3.4-OVERFLOW | The pending-event limit records QueueOverflow before a completed baseline could produce Healthy. |
| M3.4-CAPACITY | Baseline plus buffered instances exceeding capacity publish no partial baseline. Earlier loss survives a retry. Live records also stay bounded. |
| M3.4-METADATA | Excess baseline entries and oversized boot tokens fail before retention. |
| M3.4-STREAM | Foreign source generations cannot mutate the records or the active deadline. |
| M3.4-STOP | Cancellation, deadline and source disconnection release pending events and keep the generation inactive. |
| M3.4-UNCERTAINTY | Unknown loss visibility or a reported failed baseline stays degraded after a later successful baseline. |
| M3.4-TIME | Snapshot start cannot precede readiness and completion cannot precede start. |

Limits are caller-configured nonzero counts for buffered events and evidence
records, plus a maximum byte length for each boot token. The existing health
reducer also caps receipt IDs. This module has one owner. A future Windows
adapter must provide its own synchronized callback transport and actual
source readiness, capture outcome, scope and loss evidence.

The API accepts minimized instances from a single reviewed identity domain.
The snapshot owner must report partial or failed capture through
report_baseline_failure. It must advance the current monotonic clock before
processing delayed input. Reattachment requires a new generation.
